# Authored trailer intro

The intro uses the original Stick War 2 trailer supplied by the user. Its animation, artwork, music and effects remain attributable to their original creators; the conversion does not claim authorship of that material. Original imagery and on-screen credits are retained. DeadWarrior 2 is an independent project. This cinematic work does not complete the campaign: ten of fourteen missions are currently implemented.

The supplied file is `595764_stickwar2trailermay21fixla.swf`, 14,267,993 bytes, SHA-256 `a2a1bc496bb9e784fa4f5650c0368e0c3faf0bfda3fa3350979aa9f4651ef4ac`. It is a separate trailer input from the campaign game SWF. Inspection found SWF 10, ActionScript 3, a 720 by 480 stage, 30 fps and 3,235 root frames. The original file and the working source copy are unchanged.

Playback starts at authored frame 3, after the loading/start frames, and includes frame 3,235. The 3,233 displayed frames occupy exactly `3233 / 30` seconds, or 107.7666667 seconds. Source frame numbers are retained in both the picture table and the sound-event table. The native player reads prepared images and PCM audio; it does not execute a SWF or require Flash at runtime.

## Capture and composition

`tools/reference_trailer.py` and `tools/reference/TrailerObserver.as` capture the source in an isolated Adobe standalone player. The observer retains the authored timeline and scripts. Twelve reference samples use the source's 30 fps clock. The complete offline capture uses 15 fps so that every authored frame can be collected. Only the diagnostic all-frame copy removes the root streaming-audio tags, preventing that stream clock from skipping pictures during slow extraction; the original source file is preserved. Sound is extracted separately.

The wide export is 1280 by 720. Outside the camera sequence, the original picture receives uniform scale 1.5 and horizontal offset 100. Source shape 18 is an authored black matte with transparent picture content. Its horizontal extent is widened by `32 / 27`, anchored around source x 360; foreground figures are not stretched. During the camera segment beginning at frame 2,614, the original `VCam_AS3_134` horizontal camera width receives the same factor, and its render surface becomes 1280 by 720. Original vertical framing, camera motion, rotation, filters and color effects remain part of the captured result.

Uniform source screen fills also need to cover the newly exposed sides. The final observer extends only the existing white/black rectangle effects, masked to the missing lateral regions and placed beside their source objects in the original depth order. It preserves the authored objects' matrices, color transforms and alpha progression. Global placement is composed from local parent matrices: the source camera's bitmap-cache state can leave Flash's concatenated-matrix readback stale. Twenty paired captures from the same EXIT_FRAME verified 15,552,000 central pixels exactly, original effect properties and unchanged camera/partial-panel controls. The final full capture verifies the expected 404 extensions across 384 affected frames; eight approved full-frame samples also matched their paired-reference images. These checks are recorded in `work/intro-screen-fill-v7-checks.json` and `work/intro-wide-final-capture-checks.json`.

This is a fixed capture of an authored performance, with a measured limitation. An earlier export's twelve 30 fps wide samples and corresponding complete-capture frames produced ten exact RGBA matches. Frame 877 differed at 923 pixels; frame 1,769 differed at 11,045 pixels. Several source animation clips use `Math.random()` to choose their starting phases, which is a possible source of variation, but these two differences have not been attributed conclusively. The historical comparison is recorded in `work/intro-reference-clock-comparison.json`. The same-EXIT_FRAME screen-fill comparison avoids this uncertainty. The all-frame lossless checks below establish equality to the final exported capture, not pixel identity across every independent Adobe replay.

## Lossless resources and native decoding

`tools/pack_intro_frames.py` writes opaque PNG keys and RGB XOR deltas. A key is a byte-for-byte copy of its captured PNG. A delta is chosen only when smaller, and its RGB bytes are XORed with the preceding reconstructed picture; alpha remains 255. A key is forced after at most 29 consecutive deltas. The runtime manifest is published only after the complete capture manifest exists and all reconstructed RGBA frames match their captures. Incomplete PNG writes are rejected until their IEND chunk is present.

The final corrected pack contains 2,212 keys and 1,021 deltas. Captured PNGs total 1,284,178,783 bytes; packed PNGs total 1,003,531,894 bytes, about 21.85% fewer PNG bytes with no changed RGBA pixels. Those are resource sizes, not a future release archive size. `frames.tsv`, `frame-hashes.json` and `pack-report.json` add 334,842 bytes.

`src/intro_movie.cpp` implements the presentation clock, key/delta reconstruction, seeking and sound-event dispatch. Repeated presentation of the same frame does not decode it again or repeat its sound events. Seeking reconstructs from the applicable key and does not replay historical effects. The optional legacy-resource fallback is not evidence that the intro is present; a release containing the feature must explicitly verify its resources and playback.

An isolated Windows check passed all 3,233 final corrected RGBA hashes through the product `IntroMovie` reader and Windows PNG decoder with bounded prefetch enabled. It also checked twelve backward/random seeks, the longest key-plus-29-delta chain, nineteen event frame/path/order entries, the two events at frame 2,634, restart, clock catch-up and completion at `3233 / 30`. The final frame-hash manifest SHA-256 is `89304ced60bfa35050d123cdcb67da0ccc149aa58ef21f5d3829d97fa4b12322`; the complete readback is recorded in `work/intro-final-native-assets/checks.json`.

Ordinary forward delta decoding uses at most three working 1280 by 720 RGBA vectors: the published previous picture, the next canvas and the decoded delta. Their combined pixel storage is 11,059,200 bytes. This excludes PNG/GDI+ scratch, compressed buffers, metadata, GPU copies and any extra consumers retaining older shared pictures. It is not a bound on total process memory. The offline packer separately uses at most two persistent raster arrays, 7,372,800 bytes, with its own codec/runtime exclusions.

The final prepared CPU check reported PNG decode p50 10.6295 ms and p95 14.3253 ms on the local verification machine. These measurements include local file access and decoding, and exclude rendering, audio and real-time pacing. They do not establish game FPS or universal playback performance.

## Bounded PNG prefetch and Windows timing

`IntroFrameCache` uses one CPU worker to prepare upcoming PNGs. The requested frame takes priority over obsolete queued work after a forward skip or seek. Clearing playback invalidates completed and queued work by generation and stops scheduling new work. Any older decode is discarded when it returns, after which the worker waits. Clear does not wait for that decode; destruction joins the worker. Decoder failures are stored under their frame index and rethrown only when that frame is requested. The worker performs no GPU operations.

The cache reserves at most eight slots across completed frames and its one in-flight decode. This is additional to the movie's three working RGBA rasters described above. At 1280 by 720, these designated eleven pixel buffers contain at most 40,550,400 bytes. Additional consumers retaining returned or shared pictures, PNG/GDI+ or SDL codec scratch, compressed data, metadata and GPU copies are outside this accounting; this is not a bound on total process memory. The standalone cache probe verifies exact pixel values, sequential lookahead, forward/backward seeks, skipped frames, cancellation generations, indexed exceptions, capacity one and destruction during decoding. Twenty synchronized test runs passed in `work/intro-cache-final-checks.json`.

With prefetch enabled, the product reader again passed all 3,233 exported RGBA hashes, twelve backward/random seeks, the maximum key/delta chain, nineteen sound events and the final clock transition. The readback is recorded in `work/intro-prefetch-assets/checks.json`. Reconstruction-request counts and actual worker decoder calls are separate counters; seeking and discarded speculative work can increase worker calls without changing the presented pixels. In the instrumented frontend, `png_ms` measures the request's wait for a decoded frame, rather than CPU time spent inside the worker.

Isolated Windows playback measurements used the same prepared resources and harness before and after prefetch. Each resolution ran for twenty seconds without PNG captures or display changes during the measurement. The first two seconds are reported separately in the raw evidence; the table covers the following approximately eighteen seconds.

A later capture or resource revision requires its own pixel and playback checks.

## Reproducing the frame check

The Windows all-frame reader can be built separately from the game with `cmake --build build/windows --config Release --target intro_assets_probe`. After prepared resources are available, run `build/windows/Release/intro_assets_probe.exe assets/intro work/intro-assets-check --prefetch`. It checks the actual PNG decoder, reconstructed RGBA hashes, sound-event ordering, seeks and completion clock. It is an optional Windows asset check; the common deterministic CTest suite remains separate. The SDL loader uses CPU surfaces in its worker, as permitted by the documented [SDL_LoadPNG thread-safety contract](https://wiki.libsdl.org/SDL3/SDL_LoadPNG); GPU texture updates stay on the frontend thread.

## Audio

`tools/build_intro_audio.py` parses the original root `SoundStreamHead`, `SoundStreamBlock`, `DefineSound` and `StartSound` records. Its compressed payloads match the independently exported FFDec files. Music remains separate from the seventeen effect WAVs so the existing Music and Sound switches retain independent control. All output WAVs are PCM16 stereo at 44,100 Hz; there are nineteen root events, including the original ordered pair at frame 2,634. The nested preloader sound 45 is excluded.

The score concatenates the source's 3,084 MP3 blocks, skips the initial 1,677 native-rate samples, and starts at source frame 5. Thus the music WAV has 2,940 samples of initial silence relative to frame 3. Its complete duration is 4,752,510 stereo sample pairs, with 216,975 trailing silent pairs, about 4.92007 seconds. No new fades, normalization or effect mixing are applied.

Event sounds are trimmed by their native `SeekSamples` and `SoundSampleCount` before resampling. Sounds 1459 and 1651 use 22,050 Hz and a native seek of 1,673 samples. The native-rate interpretation follows JPEXS's decoder and PCM trimming order. Sound 1651's authored envelope has levels 11,667 and 11,419 at position zero; because the source sound is mono, their mean, 11,543/32,768, is applied to both output channels, as specified for mono envelopes. See the [Adobe SWF specification](https://open-flash.github.io/mirrors/swf-spec-19.pdf) and [JPEXS SoundFormat implementation](https://raw.githubusercontent.com/jindrapetrik/jpexs-decompiler/master/libsrc/ffdec_lib/src/com/jpexs/decompiler/flash/types/sound/SoundFormat.java).

Sound 1680 contains 135 trailing non-audio bytes, including an ID3v1 record. Excluding them from MP3 decoding produces the same PCM as decoding the complete original payload. The final stream block at frame 3,088 declares zero samples yet contains an MP3 frame and seek -2,039. The continuous MP3 payload is retained, and this terminal anomaly is recorded rather than assigned an invented trim. All 3,083 preceding seek relationships match the source's 1,470-sample frame progression.

`assets/intro/audio-report.json` records the source values, output lengths, PCM/WAV hashes and limitations. No Adobe audio loopback comparison has been performed. FFmpeg decoding, 22.05-to-44.1 kHz resampling and final PCM envelope quantization are not claimed bit-identical to Adobe. Perfect audio/video synchronization across the two runtimes is therefore not asserted.

The native file-audio APIs use unity gain for these already prepared WAVs. Windows converts its source-voice sample count using that WAV's sample rate. The existing SDL mixer runs at 48,000 Hz stereo, so its interleaved float cursor is divided by 96,000 to obtain seconds. File music and movie effects can pause, and movie-effect cleanup preserves ordinary UI effects, narration and music. Named background music retains its prior continuity behavior. Windows file-clock/category checks and the existing 187-sound registry/loop test passed; platform frontend playback remains a separate release gate.

## A future release

The intro is private work after preview.12. None of these resources or source changes have been added to a new public release by this documentation step. The existing packaging code already extracts every `assets/` entry from a seed and installs that directory into the platform package, so it can carry `assets/intro` without a new container format. It still requires a clean, verified seed containing the new resources. The final corrected intro folder contains 3,256 files and 1,035,307,558 bytes; adding only that folder to the frozen preview.12 payload would yield 18,039 files. Final package counts and download sizes must be measured after staging.

The maintainer preparation pipeline currently accepts the campaign SWF only. Trailer preparation needs its separate supplied input, provenance check, observer capture, frame packing and audio builder; it must not be silently treated as part of the campaign SWF extraction. Public source updates need an explicit allowlist for the intro core, platform integration, builders, observer, tests and this document. Generated captures, SWFs, WAVs and PNGs remain outside public source Git history, as required by the repository audit.

Future release validation must require intro availability and animation, multiple original frame states including a delta and the camera segment, skip/end/restart behavior, pause and channel switches, and packaged resource hashes. The Windows all-frame hash proof does not automatically verify Linux or either Mac decoder. Their final executable reports must exercise the feature too. New validation helpers must use the final registered CTest count, source SHA, exact executable and measured payload counts rather than preview.12's fixed nineteen tests and 14,783 files. Existing four-platform build, checksum, anonymous-tag/download and freeze gates still apply. Build from the frozen released payload plus approved intro changes; do not copy unrelated private future-mission assets into a seed or alter published preview.12 packages.
